IterTrip · Agent 对话前端提案

Agent 做完一轮活，应该怎么被看见？

同一轮真实消息（用户要求补第三天时间 → 查交通 → 发现冲突 → 给出候选），三种呈现方向。切换方案与状态，比较信息密度、信任感和操作成本。

A

执行收据

推荐 · 日常默认

对话保持安静。过程收成一行「查了 2 段交通 · 调整 3 处停留 · 34 秒」，需要时再展开；视觉重量全部留给待确认的修改。

优点
省空间、不吵、重点明确
代价
过程不主动可见，信任靠收据摘要
实现
纯前端；现有 trace 足够
适合
日常使用；长对话
B

任务时间线

透明优先

一轮 Agent 是一张任务卡：理解、查询、发现冲突、复核、候选都在同一条时间线上。出问题时最容易解释。

优点
最透明；复杂修改可追溯
代价
占垂直空间；长会话滚动多
实现
纯前端 + 文案改写
适合
演示、调试、复杂日程
C

分阶段对话

对话感优先

把「查交通 → 发现冲突 → 给出方案」拆成几条短消息，像 Agent 在逐步汇报。节奏清楚，但消息数量最多。

优点
有对话感；每步都好读
代价
消息多；长会话更吵
实现
可前端派生；模型口吻需后端补事件
适合
想让 AI 更有存在感

建议组合：A 作为默认收据，展开后使用 B 的时间线；提案卡三案共用。日常安静，需要排查时不丢信息。

先分清：后端到底发了什么

Agent 路径的 SSE 只有 stage / ping / trace / reply / error；真正的改动在 reply.agent_proposal，候选路线由前端同构派生。

必须显示 可折叠 仅开发/诊断
后端消息何时出现前端位置默认
stage全程状态胶囊 / 收据首行：正在理解、正在生成（N/M）、正在查询一句话状态
provider trace开始时间线首步：受约束操作模式、轮次与时长预算细节折叠
llm trace每轮「分析要求 / 生成候选 / 复核」；token 只在技术细节轮次可见
