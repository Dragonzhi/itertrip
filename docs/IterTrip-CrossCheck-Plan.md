# IterTrip 多模型交叉核查模块（Cross-Check）技术方案

> 版本 v0.1 · 2026-09-14 · 定位：IterTrip 内部模块，先独立验证再接入
> 一句话：用多个异构大模型并行核查行程中的事实性陈述，聚合裁决后给每条信息打上置信度，把「AI 生成的行程」变成「经过交叉核实的行程」。

---

## 0. 一页摘要

| 项 | 内容 |
|---|---|
| 解决什么 | AI 旅游规划的幻觉问题：开放时间、票价、班次、歇业等错误信息导致用户现场扑空 |
| 怎么解决 | 分层 MoA 架构：检索层统一取证 → 异构模型并行独立作答 → 裁决模型汇总裁决 → 输出共识结论 + 分歧点 + 置信度 |
| 学术依据 | Mixture-of-Agents（arXiv 2406.04692，ToG 2024）：多模型分层聚合可超越单个最强模型 |
| 核心卖点 | 信源异构性。不同模型的搜索后端不同（字节生态 / 阿里生态 / 独立爬虫），天然形成真正的多信源交叉验证，治单一引擎盲区 |
| 形态 | W1-W2 做成 CLI 管线跑通并出评测数据，W3 接入 IterTrip Web 端，行程页展示可信度徽章 |
| 成本量级 | 单份行程全量核查约 0.1~0.5 元，缓存与抽样后可再降一个量级 |

---

## 1. 问题定义

### 1.1 痛点

AI 生成行程中，以下信息错误率最高、错误代价最大：

- **时效性事实**：景点开放时间（旺季/淡季/周一闭馆）、临时管制、店铺歇业
- **价格事实**：门票、缆车、交通票价、优惠规则
- **衔接事实**：班车班次、末班车时间、码头渡轮时刻、换乘可行性
- **状态事实**：装修中、汛期关闭、需预约

这些信息的共同点：**有客观对错、随时间变化、单模型容易幻觉、错了用户会真实受伤**。

### 1.2 为什么单模型 + 联网搜索不够

1. 单一搜索后端 = 单一信息茧房（百度的结果和抖音生态的结果差异巨大）
2. 单模型幻觉无法自察，错误会以流利的口吻输出
3. 用户无法区分「AI 很确定」和「AI 在编」

### 1.3 模块边界

- 核查对象：行程中可验证的客观陈述
- 不核查：主观推荐（「值得去」类内容标注为推荐性内容，不参与裁决）

---

## 2. 核查对象抽取

不是所有句子都要核查，先做结构化抽取控制成本。

### 2.1 分级

| 级别 | 定义 | 处理 |
|---|---|---|
| L1 硬事实 | 价格、时间、班次、地址、电话 | 全量核查 |
| L2 软事实 | 小众但可查（观景台视角、徒步路线现状） | 抽样核查（每日行程抽 30%） |
| L3 主观推荐 | 个人偏好类描述 | 不核查，UI 标注「推荐性内容」 |

### 2.2 抽取方式

主行程生成模型输出时同步产出结构化核查清单（JSON Schema）：

```json
{
  "claims": [
    {
      "id": "c001",
      "text": "九寨沟旺季门票 169 元 + 观光车 90 元",
      "type": "price",
      "poi": "九寨沟",
      "date_sensitive": true,
      "level": "L1"
    }
  ]
}
```

要点：抽取与生成同一次调用完成，只多输出一个 JSON 字段，几乎零额外成本。

## 3. 架构：三层 MoA

```
用户行程
   │
   ▼
[抽取层] 结构化核查清单（同生成调用完成）
   │
   ▼
[检索层] 统一搜索管线：为每条 claim 拉取证据材料
   │        ├─ 博查 / Bing API（通用网页）
   │        └─ 各模型自带联网能力（差异化信源）
   ▼
[并行作答层] N 个异构模型，基于检索材料独立作答
   │        （互不可见，避免锚定效应；各自给出结论+来源+ confidence）
   ▼
[裁决层] aggregator 模型汇总 N 份答案
   │        输出：共识结论 / 分歧点 / 最终置信度 / 引用列表
   ▼
[输出层] 行程页可信度徽章
```

### 3.1 关键设计决策

1. **并行作答互不可见**：任何模型先看到别人的答案就会锚定，独立作答才能保住分歧信号的价值
2. **裁决与作答分离**：aggregator 只做汇总裁决，不自己重新搜索，职责单一降低出错面
3. **分歧是资产**：答案一致 → 高置信；答案打架 → 黄色标注并展示分歧点给用户。分歧本身是信息，别试图强行抹平
4. **降级策略**：N=3 起步；单模型超时/失败用 N-1 结果；全失败标灰色「未核实」，绝不阻塞主流程

### 3.2 输出 UI（绿黄灰三色徽章）

- 🟢 绿：N 个模型共识一致，附引用来源
- 🟡 黄：存在分歧，展开显示各模型结论与来源，引导用户以官方渠道为准
- ⚪ 灰：核查失败或证据不足，标注「未核实」

体感设计：主行程先正常输出，核查异步后台跑，完成后徽章逐条亮起。用户感知到「这个产品在认真帮我查证」，体验差异极大而成本极低。

## 4. 模型选型（国内直连、异构优先）

### 4.1 选型原则

1. **异构 > 同构**：不同厂家的模型 + 不同搜索生态，信源多样性是本模块的核心价值
2. **便宜模型普查，强模型裁决**：作答层用高性价比模型，裁决层用推理/长上下文更强的模型
3. 先跑 benchmark 再锁定，以下为初始候选（以实际 API 价格与能力为准）

### 4.2 初始组合

| 角色 | 模型 | 理由 |
|---|---|---|
| 作答 1 | DeepSeek-V4-Flash | 便宜 + 推理强，幻觉率相对低 |
| 作答 2 | Qwen3.8-Flash | 快 + 便宜 + 高并发 |
| 作答 3 | 豆包 Seed-2.1 | 字节生态，抖音本地生活数据对旅游场景有独特覆盖（餐厅营业状态等） |
| 裁决 | Qwen3.8-Max 或 Kimi-K3 | 长上下文吃得下多份检索材料 + N 份作答，裁决质量优先 |

备选：Kimi-K2.5（超长材料调研）；文心（百度索引补充新闻/官方通告类信源）。

### 4.3 Prompt 要点（作答层）

- 输入：claim + 检索材料
- 要求输出 JSON：`{conclusion, evidence_quote, source, confidence}`
- 明确指示：「证据不足时必须回答 INSUFFICIENT，禁止推测」

### 4.4 Prompt 要点（裁决层）

- 输入：claim + N 份独立作答
- 要求输出：`{verdict, agreement_level(0-1), disagreements[], sources[], advice}`
- 关键规则：多数一致时仍需检查引用是否真实支撑（防「集体幻觉」）；无法裁决时诚实输出 UNRESOLVED

## 5. 成本估算（数量级，以实际 API 价格为准）

### 5.1 单条 L1 陈述核查

| 环节 | token 量级（输入） | 说明 |
|---|---|---|
| 检索材料组装 | ~2K/模型 | 每个作答模型各一份 |
| 作答输出 | ~300/模型 | JSON 结构化 |
| 裁决输入 | ~7K | claim + 3 份作答 + 摘要 |
| 裁决输出 | ~400 | |

国内主流模型百万 tokens 输入大致在 1~8 元、输出 2~16 元区间（各家差异大，部署前实测）。按此估算：**单条核查约 0.005~0.015 元**。

### 5.2 单份行程

3 天行程约 30 条 L1 陈述全量核查：**约 0.15~0.45 元**。

### 5.3 优化手段

1. **缓存**：key = (POI, 陈述类型, 月份)，月级时效缓存，热门 POI 命中率会很高
2. **分级核查**：L1 全查、L2 抽 30%、L3 不查，实际成本可压到全量的 50% 以下
3. **异步批处理**：错峰跑，部分厂商夜间半价

### 5.4 月成本场景

| 场景 | 估算 |
|---|---|
| 个人 demo（日均 10 份行程） | ~50 元/月 |
| 1000 用户（每人 1 份行程/月，缓存后） | 数百元/月量级 |

结论：成本不构成障碍，真正的工程价值在「把钱花在 L1 上」。

## 6. 工程要点

1. **并发编排**：Python asyncio 并行调用 N 个模型，单模型超时 15s，整体超时 30s
2. **异步架构**：核查队列与主行程生成解耦（FastAPI + 后台任务 / 消息队列），绝不阻塞主流程
3. **缓存**：SQLite（MVP）→ Redis（接入 Web 后）
4. **评测集**：构建 100 条旅游事实测试集，其中混入 30 条故意错误（错价格、错时间、错班次），测三个指标：
   - 错误捕获率（能不能抓出埋的错误）
   - 误杀率（把正确信息标黄的比例）
   - 单条均成本
5. **合规**：所有核查结果标注「AI 交叉核查，仅供参考，请以官方渠道为准」；对价格/时间类信息始终保留官方渠道链接

| 周 | 目标 | 产出 |
|---|---|---|
| W1 | CLI MVP：单条陈述核查管线跑通（3 作答 + 1 裁决），终端报告 | 可运行的 repo + demo 录屏 |

## 8. 面试叙事要点

1. **为什么异构模型**：单一搜索后端即信息茧房；不同模型的生态信源互补（抖音本地生活 vs 百度索引 vs 独立爬虫）。引 Search Arena 与 ChatALL 的动机
2. **为什么分层裁决**：MoA 论文结论，分层聚合的弱模型组可逼近强模型；职责分离降低出错面
3. **分歧处理哲学**：分歧是信息，抹平分歧等于丢失信息。置信度展示优于强行给单一答案
4. **成本工程**：分级核查 + 缓存 + 抽样，把全量成本压到可忽略，体现工程判断力
5. **诚实设计**：UNRESOLVED 状态、灰色徽章、官方渠道引导。AI 产品的信任来自承认边界
6. **数据说话**：拿 W2 评测报告讲，「错误捕获率 X%、误杀率 Y%、单条成本 Z 元」，比任何形容词都硬

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型间集体幻觉（都错且一致） | 裁决层检查证据引用真实性；关键价格类 claim 强制附官方来源链接 |
| 某家 API 变动/涨价 | 作答层模型可插拔，配置化切换；保持 1 家备份 |
| 核查延迟影响体验 | 异步 + 徽章渐进亮起，主流程零阻塞 |
| 评测集标注主观 | 只收有官方来源可对照的 L1 陈述，争议样本双人标注 |
