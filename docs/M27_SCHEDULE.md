# M27 · 时间排程、固定预约与关键事实

> 2026-09-30 · 已实现，自动化与构建通过；手机排版、真实场馆资料与真实预约的人工使用验收尚未记录。
> 对应范围：[开发方向 M27](NEXT_DEVELOPMENT_DIRECTION.md)。下一阶段：M28 PWA 与离线查看。

## 使用入口

1. 在规划视图确认出发日期，设置每天开始／结束时间。不从酒店出发时，“开始”表示已经到首站，不包含出发地到首站的交通。
2. 点击每站的「安排／预约」，设置停留分钟及用户设置／估计、参观／用餐／休息、必去、锁定与规划已完成状态。没有默认游玩时长，原攻略 `time` 字符串保留。
3. 记录固定入场时段、车次占用时间或酒店入住边界的日期、开始、结束、状态与入口。打开链接后自行办理并记录；网站不下单、不判断订单是否真实成功。
4. 开放资料先查阅对应地点的官方公告或地图资料，再填开放／关闭、最后入场或明确无单独限制、闭馆通知、预约要求、适用日期与星期、来源链接。勾选「我已查阅」记录查阅时间及地点名称；编辑任意值后需重新确认。可保留多条资料，矛盾时提示核对。
5. 查询相邻交通段，检查时间结果。调整时间、缓冲、方式或站点后自动重算，保存／撤销／重做沿用同一历史栈。

资料线索搜索使用已有 Tavily 兼容配置。没配置或请求失败时仍可手工查阅并记录来源，不阻断编辑与导航。返回的标题、链接、摘要是待核对线索，未自动识别“官方网站”，也不被自动解析成营业规则。**资料的确认来自用户查阅，不宣称系统已独立核实页面内容。**

## 最终数据契约

所有新字段可选；后端 Pydantic、前端类型、JSON／HTML 导入导出均保留。

| 字段 | 内容 |
| --- | --- |
| `day.schedule` | 当天 `start`／`end`，严格 `HH:mm` 才能参与计算 |
| `place/hotel.visit` | `duration_min`、`duration_source=user/estimate`、`kind=visit/meal/rest`、`required`、`locked`、`completed` |
| `visit.reservation` | `type=entry/train/hotel/other`、ISO `date`、`start/end`、`status=needed/pending/confirmed/cancelled`、`url` |
| `place/hotel.opening[]` | `place_name`、`open/close/last_entry`、`entry_policy=unknown/none/last_entry`、`closed`、`reservation_required`、ISO 星期 `weekdays`（1=周一；空=每日）、`valid_from/valid_to`、`source_kind=official/map/user`、`source_url`、`checked_at`、`confirmed` |
| `hotel.prices[]` 增量 | 逐条 `source_url/queried_at`、`check_in/check_out`、`room`、`occupancy`、`cancellation`、`unit=night/stay`、`breakfast_known`（未知不当作无早） |

预约地点就是挂载记录的站点，不重复保存一个会漂移的地点名。开放依据额外记录查阅时的 `place_name`，改名后不继续认定资料适用。

预约 `confirmed` 表示用户记录已确认，不代表网站验证了订单。`visit.completed` 是随行程导出的规划记录；M25 的途中到达／完成进度仍存独立 localStorage、不进撤销栈、不随路线导出。两者都会阻止 AI 自动移动；规划记录已完成的站点在出行视图跳过，要恢复需在安排中取消。

## 计算与诚实边界

确定性逻辑集中于 `shared/schedule.js`，React 与导出 HTML 共用；结果在读取时派生，不向 route 写入过期的到达时间。

- 首站／酒店出发 → 交通分钟（向上取整）+ 单段缓冲 → 到达 → 开放或预约前的等待 → 停留 → 离开。等待独立于交通和停留。
- 车次记录占用到车次结束，不能靠把停留改短缩短火车运行时间；赶不上车次或车次不适用于当天时停止后续时间，不假装仍能乘车。酒店默认是到达／入住边界，不把住宿一夜当作当天游玩时长。
- 固定开始迟到、结束越界、最后入场、关闭、当天结束、跨日期预约以及固定时段互相重叠，分别列出触发时间和原因。
- 日期未知／推断、开始结束缺失、停留估计或未知、交通缺失／过期、资料待确认／有效期不符、最后入场规则未知、预约待办理／待确认均列为未评估。
- 开放资料未知时，不默认等待为零；本站开始与后续时间停止推进。已知到达仍可显示。资料冲突与当天关闭亦不能继续当成正常参观计算。
- 多个适用来源值不一致，提示冲突；缺链接、查阅时间无效／在未来、地点名称变化都不能认定资料有效。跨夜开放规则、跨夜预约、境外／跨时区评估首版不支持。
- 最完整结果仍是「当前输入下预计可行」，交通是 M26 **查询时估算**，不具备未来出发时刻的实时路况预测。15 分钟过期即停止参与计算；导出显示历史快照并提示刷新。
- 冲突只给候选：缩短停留、切换已有有效快照中更快的方式、核对后移至另一日。候选不自动执行、不宣称已找到可行替代；固定／已完成点保留，需要用户取舍时直接说明。

M22 文本闭馆规则仍是“原攻略声称某星期闭馆”的日期冲突检查，不能替代开放资料核实。`refreshClosures` 在本地每次编辑与导出渲染时幂等重写 `闭馆日：` 警告；简繁、固定／例行字样和节假日例外与后端解析口径对齐。改日期后立即重算，不依赖额外网络。

## AI 与旧响应保护

- 提示词要求保留安排，但实际保护由代码执行：后端 `engine/arrangements.py` 在坐标核验前检查，拒绝删除／移动固定、预约或已完成点及删除必去点，以 SSE `schedule-guard` 轨迹及「行程未修改」终帧说明。
- 前端 `schedule.protect` 再检查，包括仅保存在本地的途中完成进度；模型遗漏／伪造安排、开放依据或交通快照不会覆盖用户记录。
- 匹配优先稳定 ID；ID 遗漏时仅恢复可唯一识别的旧地点，不合并同名分店。酒店与普通地点不能互相冒充。
- AI、日期检查、交通查询和安排表单使用路线引用版本。生成期间编辑／撤销后，旧结果不写入。原样保存安排可以正常关闭，不生成历史帧；取消不修改。
- 手工跨天／排序保留预约本身并提示重查；删除受保护点需先取消相应约束，普通地点继续一键删除可撤销。
- diff 使用稳定地点 ID，并包含停留／预约、开放资料、起止时间、日期与报价上下文。

## 酒店搜索与比较

`POST /api/search` 现在传实际住宿日及次日离店日。每条搜索价格保留各自的来源链接与查询时间，不再把不同搜索结果合并后丢失出处。

搜索摘要提到“￥300”不能证明对应当前入住日、房型或退改条件，所以这些字段保持未知，不参与最低比较。RollingGo 只有明确返回的条件才记录，不因请求携带日期就默认所有报价符合。手工报价可补全条件与查阅时间，编辑报价后需重新确认。

仅当前入住／离店日期一致、房型／人数／退改／计价单位完整且有来源和有效查阅时间的报价进入比较；按这些条件及早餐分组，至少两条才显示「同条件最低」。旧报价继续展示及导出，缺项不误标最低。时间线、地图酒店提示与导出同步该口径。

资料线索接口：`POST /api/route/facts/search`，输入 `name/city/date`，最多 5 条线索、每条摘要最多 900 字，12 秒 HTTP 超时。密钥只在服务端，不返回到前端或导出；不抓取用户提供的任意 URL。外部文本只渲染为文本，链接仅接受无凭据 http(s)。
