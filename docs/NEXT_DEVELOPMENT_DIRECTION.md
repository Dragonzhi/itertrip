# IterTrip · 下一阶段开发方向

> 版本：v1.5 · 2026-10-01
> 状态：M25 已完成用户验收；M26 已通过自动化、构建及高德真实接口验证；M27 已实现并通过自动化与构建，待人工使用验收；M28 已实现并通过生产构建、worker 与离线 DOM 自动化，待真机安装／更新验收；M29 已实现并通过自动化与构建、Open-Meteo 国内城市公开接口验证，和风及真机使用待验收；M30 未实现。
> 依据：当前仓库代码、用户关于交通／天气／导航／UI／Agent 的讨论，以及 TREK 的公开项目文档。
> 用途：作为下一阶段范围与优先级的主文档；具体施工方案在各里程碑开工时细化，不承诺日历交付日期。

## 1. 产品方向与差异化

**把用户收藏的攻略，变成走得通、赶得上、遇到下雨也能调整的旅行日程。**

保留「攻略 → 可编辑地图 → 可带走的 HTML」主线，延伸到「检查可行性 → 导航到下一站 → 调整剩余行程」。
首批场景聚焦国内城市短途旅行，以成都、长沙等已有坐标样本验证；跨国、多时区、长线自驾留待后续。

差异化落在四件可验收的事：

1. 忠于用户攻略，保留必去点、手动修改和已预约时间；新增替代地点先作为候选展示。
2. 时间、交通和天气有数据依据，标出查询时间、估算与未知状态，解释安排的取舍。
3. 变化时优先局部调整，展示修改前后差别，用户能确认并撤销。
4. 手机上能快速看到下一站并打开导航，导出后也能继续使用。

竞品已有地图、路线和天气相关能力，不能将这些单项功能宣称为独家。当前差异化是产品假设，
需通过真实旅行使用验证。原攻略也可能过时，作者推荐不等于营业时间、坐标和票价已经核实。

## 3. 开发顺序与完成标准

按 **M25 → M26 → M27 → M28 → M29 → M30** 推进。每阶段必须形成独立可用闭环，再开始下一阶段。
信息来源和兼容性工作随对应功能完成，不能在最后补做。单模型策略、坐标护栏、撤销与导出始终保留。

| 阶段 | 交付物 | 依赖 | 用户能得到的结果 |
| --- | --- | --- | --- |
| M25 | 导航交接与手机出行视图 | 现有路线 | 看下一站、打开导航、返回后继续 |
| M26 | 独立交通段与真实耗时 | M25；地图路径接口 | 比较交通方式，知道每天移动的代价 |
| M27 | 时间排程、固定预约与关键事实 | M26 | 判断是否赶得上、是否走得完 |
| M28 | PWA 与离线查看 | M25；复用 M26／M27 数据 | 断网仍能打开已保存日程 |
| M29 | 天气评估与局部重排 | M26／M27 | 看到天气冲突，并选择可行的调整 |
| M30 | Agent 操作工具与评估 | 稳定的数据与校验契约 | AI 修改可验证，执行失败不报成功 |

### M25 · 导航交接与手机出行视图

当前进展：已完成。功能与自动化验证通过，用户于 2026-09-30 确认验收可用并要求本地提交收尾。实现、验证证据和回归步骤见 [M25 施工记录](M25_NAVIGATION_OUTING.md)。

范围：

- 地点卡、地图气泡、酒店卡和导出 HTML 提供「去这里」，首批适配高德与百度。
- 默认交接目的地，由外部地图选当前位置；另提供按上一站比较路线的入口，明确计划起点与实际位置的区别。
- 记住用户选择的地图，保留「复制地址／查看地图」备用动作。
- 手机区分规划与出行视图：出行视图突出当天、下一站、导航、已到达／已完成。
- 当前日期和进度持久化；首版完成状态由用户操作，普通外部跳转不推断已经到达。
- 延续奶油色／深绿色设计令牌；大点击区域、清楚的按钮文字、键盘标签和可见焦点同步完善。

验收：

1. Android Chrome、iOS Safari 与桌面浏览器的支持情况有实测记录；App 唤起受限时可用网页或复制地址继续。
2. 跳转处理各平台的坐标类型与经纬度顺序；GCJ-02 不重复转换，名称与地址正确编码。
3. 坐标来自城市中心、缺失或明显可疑时提示确认地点；坐标不可用时提供名称／地址搜索，避免引导到错误中心点。
4. 大型景区优先使用核实的入口；无入口数据时显示所用点位，不能假称已找到入口。
5. 返回网站或刷新后恢复当天与进度，查看／导航不产生路线撤销帧。
6. 导出 HTML 可进行单地点导航；无后端时仍可跳转，启动导航本身可能需要网络与外部 App。

不承诺整天行程无损导入所有导航软件，也不承诺跳转后外部软件保持相同路径／耗时或直接开始导航。
全天交接另行标注平台能力和途经点限制，绝不静默丢站。

### M26 · 独立交通段与真实耗时

当前进展：已实现，契约／DOM 集成／M25 回归和构建通过，并完成一组高德真实比较。Schema、接口预算、失败边界和实测数据见 [M26 施工记录](M26_TRANSPORT.md)。人工手机排版回归未单独记录。

范围：

- 为地点赋予稳定 ID，保留可用的供应商 POI ID；酒店参与每日出发／返回路径。
- 相邻地点之间建立交通段；每日有默认方式，每段可覆盖。
- 国内首选高德路径服务，经后端适配查询步行、公交、驾车方案；驾车方案用于打车比较时另说明等待／接驳未包含。
- 显示方式、距离、预计耗时、可用的费用估算、查询时间和出处；缓冲独立显示。
- 时间线展示游玩与交通两类条目，按天汇总交通时间、步行距离和已有费用估算。
- 首版保留原地点顺序；后续排序只作为可比较候选，评价真实交通代价与锁定约束。

验收：

1. 同一天可以混用步行、公交与驾车，酒店往返和换酒店当天起终点正确。
2. 拖动、删除、改坐标、改交通方式后，旧交通段失效；异步旧响应不能覆盖新路线。
3. 接口包含的步行／等车耗时不重复加算，额外缓冲与提供商估算区分。
4. 查询失败时保留路线并标「交通耗时未知」；直线连线只表示地点顺序，不冒充道路路径。
5. 对缺失或低精度坐标先提示确认，不生成貌似精确的交通结论。
6. 拖拽、交通方式修改和相关数据通过同一撤销入口；导出能展示查询快照与来源。
7. 请求去重、超时、限流与请求级预算可观测；首版按相邻地点查询，不默认请求全部两两组合。

未来日期的交通为查询时的估算，不能将当前路况承诺为未来实时情况。费用缺失记为未知，不按零元汇总。

### M27 · 时间排程、固定预约与关键事实

当前进展：已实现结构化安排、预约、开放依据记录、确定性排程、AI 约束保护及同条件报价比较，自动化／M25–M26 回归／构建通过。资料由用户查阅后记录，搜索仅提供待核对线索，不自动宣称已核实官网内容。使用方式、完整契约及限制见 [M27 施工记录](M27_SCHEDULE.md)；真机与真实场馆／预约使用仍待人工验收。

范围：

- 当天起止时间、停留时长、用餐／休息、固定预约窗口、必去与已完成状态结构化。
- 到达时间 = 上一站离开时间 + 交通耗时 + 额外缓冲；开放前到达的等待独立记录。
- 核实开放时间、最后入场、闭馆通知、预约要求；优先地点官方网站／官方公告与对应地图资料。
- 保存适用日期、来源链接、查验时间；来源冲突或缺失时不自动认定可行。
- 最小预约记录支持手工录入类型、地点、日期与时段、状态和官方入口；酒店／车次作为固定边界。
- 酒店搜索传入实际入住／离店日期；参考报价保留逐条来源与价格上下文，无法对应具体条件时不参与「最低」比较。

验收：

1. 迟到、最后入场冲突、时间重叠、超出当天结束时间有可解释结果；停留建议标明用户设置或估计。
2. 固定预约和已完成部分不被自动移动；手工冲突会被提示。
3. 日期未知、时间未知、营业规则未核实时显示未评估，不能标「全部通过」。
4. 给出缩短停留、改方式、移到另一日等候选；无可行方案时列出冲突与需用户取舍的条件。
5. 改日期／时间后闭馆日与日程结果同步重算；撤销恢复完整状态，导出一致。
6. 预约页使用核实或用户提供的链接；不自动下单、不伪造预约成功。

文件／订单 AI 导入留作此阶段后续增量，不把完整票务解析系统作为本阶段前置。

### M28 · PWA 与离线查看

状态：已实现并通过自动化与构建；真机安装、浏览器生命周期和实际部署待人工验收。见 [M28 施工记录](M28_OFFLINE_PWA.md)。

范围：

- 支持安装至主屏幕，默认恢复当前行程；缓存应用壳与打开行程所需代码。
- 保留本地优先；较大结构化数据按需迁移至 IndexedDB，已有 localStorage 数据可恢复。
- 离线显示已保存日程、交通快照、地址、备注、预约与进度；地图／接口不可用时仍可读。
- 显示缓存更新时间、离线状态、清理入口；新版本更新避免打断未保存的修改。

验收：

1. 在线加载并准备后，断网重开安装应用仍可查看当前路线；不只是已打开页面不刷新还能看。
2. 本地手工编辑与撤销不依赖网络；AI、搜索、天气刷新等联网操作明确显示不可用。
3. 离线天气／交通标为快照，联网失败不当作刷新成功；清理缓存不静默删除唯一行程或用户设置。
4. 安装与更新在 Android Chrome、iOS Safari 记录实测差异。

首版不做离线地图批量下载、云端修改队列或多人冲突同步；不缓存 BYOK 请求和带凭据的响应。

### M29 · 天气评估与局部重排

状态：已实现并通过自动化、构建及成都／北京 Open-Meteo 公开接口验证；和风凭据、生产网络和真实途中使用待人工验收。见 [M29 施工记录](M29_WEATHER_ADJUSTMENT.md)。新室内替代点保留为人工查阅提示，当前候选保留原地点，有限搜索不宣称全局最优。

范围：

- 地点标注室内／室外／混合／未知、天气敏感程度与来源，用户可改；不能仅凭名称强制分类。
- 经后端接天气数据，优先验证和风逐小时服务；如权限／预算不满足，评估 Open-Meteo，先验证国内覆盖与可用性。
- 预报带提供商、发布时间、有效时段、地点／区域、时区与数据粒度；预报范围由实际返回数据确定。
- 评估游玩窗口及交通段的户外步行；规则考虑降雨概率与强度，阈值可配置并解释。
- 打开行程或用户刷新时更新；前台可适度刷新。首版不承诺浏览器关闭后的监控／推送。
- 默认先换时段，再调整当天顺序，再考虑跨天，最后展示新增室内替代候选。
- 调整候选重新计算交通、开放／预约／结束时间；展示变更数量、交通时间、步行和费用的可用差值。

验收：

1. 模拟下午降雨时，在约束允许下调整户外游玩，原攻略地点与预约仍保留。
2. 混合／未知属性需要确认；室内替代不能忽略闭馆、预约和到达时间。
3. 仅有每日预报时只给日级建议；不编造小时雨停时间。超出预报窗口显示暂不可评估。
4. 历史天气若展示，明确与预报分开，不参与当天避雨决定；缓存跨日期或时区边界不会错位。
5. 用户预览后应用一次产生一帧撤销，取消不改路线；不存在可行方案时保留原路线并说明冲突。
6. 查询失败不阻断编辑／导航，轨迹明确缺少天气数据；不宣称一定不会淋雨。

### M30 · Agent 操作工具与评估

范围：

- 保持一个模型承担理解与说明，时间算术、地理检查和约束交给代码，外部事实交给工具。
- 把搜索地点、查交通、查天气、移动地点、设停留时长、锁定预约、检查日程等封装为明确工具。
- 模型生成领域操作候选；先验证参数、地点身份、路线版本和约束，再一次性应用。
- 结构化输出／工具调用按供应商能力启用；不支持时保留双段协议与 Pydantic 校验，业务校验一致。
- 重试、查询轮数、总耗时与成本有预算；轨迹反映真实执行，说明基于实际 diff。
- 对复杂自动重排保留预览确认；普通明确编辑继续沿用现有直接修改与撤销，不增加每轮审批。

验收：

1. 拼错参数、地点不存在、固定预约冲突或旧路线版本均拒绝操作，并给出原因。
2. 同一操作重放不重复新增地点；组合修改部分失败时整组不应用。
3. 工具超时／报错、用户停止、模型只说成功、JSON 合法但操作无效均不会显示已完成修改。
4. 新字段参与 diff／撤销／持久化／导出；供应商能力不足时仍有可用降级。
5. 真实场景评估集记录约束违反率、修改成功率、事实依据覆盖率、延迟与 token／工具成本。

内部工具先做好；对外 MCP、复杂 Agent 框架、多模型互评、插件市场不列入本轮范围。

## 4. 数据与实现原则

地点身份、交通段和出行进度已在 M25／M26 落地；访问安排、关键事实记录和派生日程已在 M27 落地；天气等后续契约在对应阶段细化 Schema。

| 对象 | 最小职责 |
| --- | --- |
| 地点身份 | 稳定 `id`，可选供应商与 `provider_id`；名称变化不改变身份，同名分店不合并 |
| 访问安排 | 停留时长、预约窗口、锁定、室内外属性；缺失／未知不填假默认事实 |
| 交通段 | 起终点 ID、方式、距离／耗时／可用费用、提供商、查询时间与状态已落地；道路几何待扩展 |
| 日程结果 | 按日期计算的到达／离开／等待时间和冲突；标注所用路线版本 |
| 事实依据 | 字段、值、来源、查验时间、有效日期范围、冲突／待确认状态 |
| 天气快照 | 地理区域、时区、发布时间、有效时间与粒度、提供商与数据状态 |
| 出行进度 | 当前日与已完成访问；与规划快照分开保存，导航／查看不进入路线撤销栈 |

兼容要求：

- 新字段先可选，旧 JSON／HTML 可导入；首次规范化分配 ID 后持久化，不能每次渲染重新生成。
- 同步更新后端 Pydantic、前端类型、API、diff、撤销、导入、模板与手工编辑；避免后端丢新字段。
- LLM 未回显字段时保留用户已确认的身份与约束；明显冲突走校验，不按名称强行匹配覆盖。
- 路线与计算快照分离；根据 ID、坐标、日期／出发时段、方式、偏好与提供商生成请求签名。
- 取消、重排、手改后以签名／版本阻止旧响应落盘；撤销后显示旧快照的时间，或标为待刷新。
- 交通／天气／事实告警独立于用户 `note`，各模块只更新自己负责的告警。
- route 坐标继续统一 GCJ-02；外部服务需要其他坐标系时在适配边界转换，不能修改整个 route 的基准。
- 外部信息、网页和记忆是资料，不是执行指令；记忆中的时效事实仍需要来源与有效期。
- 查询工具不直接写路线；候选通过校验后统一走现有变更／撤销入口，输出实际差异。

建议扩展位置：导航 URL 纯函数放前端 `lib`；交通／天气／排程／事实适配放后端 `engine` 与相应 API；
薄化 `chat.py`、`Plan.tsx` 的职责，避免继续把所有流程堆进两个大文件。不为此重写现有框架。

## 5. 数据接口与 UI 的开工检查

接接口前用真实样本验证权限、配额、费用、覆盖、坐标系、数据更新时间与关键字段；具体套餐尚未选择。
查询入口由后端封装，凭据不进 route／导出／日志。缓存按供应商规则和时效设置，有请求级预算与失败降级。
不以「无需 key」推断可无限调用或商业免费，不默认用公开演示路由服务承担生产负载。

UI 按用户决策组织，保留现有主题：

- 手机出行视图：当天摘要 → 下一站／导航 → 游玩与交通 → 相关冲突 → 调整剩余行程。
- 桌面规划视图：地图与时间线联动，AI 按需展开，保留地图可视空间。
- 交通方式比较显示取舍；数据更新时间和依据可展开，不把工程参数塞进主流程。
- 地点、交通、预约、天气使用统一卡片层次；金额／时间便于比较，告警不只依赖颜色。
- 正式界面设计实施前给出方向草稿，再细化选定方案；本方向文档不等于已确定全部视觉布局。

## 6. 验证、反馈与范围控制

每阶段选择适合的纯逻辑、接口与浏览器验证，不依赖真实付费接口完成全部回归。
固定样本覆盖：同名分店、城市中心坐标、酒店往返、换酒店、固定预约、未知时间、下雨换时段、无可行方案、
用户迟到、取消／接口失败、旧 JSON 导入、导出再导入、手机跳转与返回、离线冷启动。

完成声明至少附：改动范围、验收证据、失败降级、已知限制；真实接口使用单独记录提供商与测量日期。
前端改动通过构建，后端改动通过相应导入／接口检查。文档更新不能把未验收里程碑改成已完成。

真实旅行反馈采用用户自愿反馈，不新增默认行为追踪。优先观察：

| 问题 | 记录内容 |
| --- | --- |
| 是否真用来出行 | 导航是否打开正确地点、回来后是否继续使用 |
| 时间是否可信 | 预计与实际移动／停留时间差，等待或入口遗漏 |
| 调整是否有价值 | 是否接受候选、原因、预约是否保留、是否撤销 |
| 离线是否够用 | 断网时能否找到地址与日程，是否存在加载空白 |

下列方向暂缓：账号／云同步、实时多人协作、分账与完整旅行管理、自动预订、平台价格抓取、
内容平台登录采集、地图底图重写、完整导航引擎、全量离线地图、复杂插件市场。
`docs/TODO.md` 的记忆档案携带与断流策略仍是待反馈事项，不因此自动排进本轮。
